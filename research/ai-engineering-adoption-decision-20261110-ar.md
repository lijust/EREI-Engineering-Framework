# مذكرة قرار: كيف نجعل AI ينفذ مشروعاتنا بمستوى احترافي دون إعادة بناء أدوات موجودة؟

**التاريخ:** 2026-11-10  
**حالة القرار:** **RECOMMENDATION / NOT IMPLEMENTATION AUTHORIZATION** — تحتاج مراجعة واعتماد المالك قبل تثبيت مكونات أو تعديل عقد التشغيل.  
**حقيقة مفصلية:** الصور التسع تصف **180 مفهومًا يغلب عليها هندسة تطبيقات الويب**؛ لا تمثل مواصفة نموذج AI بأوزان جديدة ولا معيارًا واحدًا يكفي لكل أنواع المنتجات.  
**مرجع الحقائق:** [180 مفهومًا كاملة](./web-engineering-9-domains-180-concepts-ar.md) و[مقارنة المشاريع الأصلية](./ai-engineering-repo-landscape-20261110-ar.md) و[ADR-0006](../adr/ADR-0006-EVIDENCE-FIRST-NO-AUTONOMOUS-LEARNING.md).

## 1. تحديد الهدف الحقيقي (بدل بناء Framework كغاية)

**المخرجات المطلوبة:** حين نطلب إنشاء/إصلاح مشروع برمجي، يتعرف الوكيل على stack ومستخدمين ومخاطر المنتج، يختار من المجالات التسعة ما ينطبق، يصمم أصغر حل مبرر، ينفّذه داخل صلاحيات محددة، ويُثبت جودة الناتج باختبارات/قياسات حقيقية مع توثيق قرار بشري عند الخطر.

**معايير الفشل:** فرض كل التقنيات الـ180؛ توليد مواصفات أكبر من التعديل؛ إدعاء PASS دون تشغيل؛ استخدام library جديدة بلا سبب؛ تخطي security/authorization؛ تطبيق SSR/React على desktop؛ تكرار سجل تعلم ذاتي؛ إنشاء runner أو Docker stage بلا حالة تشغيلية تثبت الحاجة.

**عوامل النجاح:** correctness، الأمن/خصوصية البيانات، الإتاحة عند وجود واجهة، أداء مقاس عند الحاجة، الحد الأدنى من الملفات/التعقيد، قابلية الصيانة، وقت الإنسان، وكلفة النموذج الفعلية. لا يمكن إثبات هذه النتائج بالنصوص وحدها.

## 2. المعمارية البديلة المقترحة — إعادة استخدام لا إعادة كتابة

```text
[Project context + AGENTS.md + minimal 9-domain applicability profile]
                             |
                 Task classification: bug / feature / design
                             |
       small bug ------------+------------ new feature / architecture
          |                                     |
       direct agent                     Spec Kit (selected workflow)
       + tests                        (or OpenSpec as alternative)
          |                                     |
          |                   optional EGM fresh-context review
          |                   only for costly architectural decisions
          +------------------+------------------+
                             |
             Implementation with scoped permissions
                             |
       Existing deterministic checks / real measurements
        (unit, API, E2E, security, accessibility, CWV)
                             |
              Human decision + existing evidence
```

**قرارات واجبة للحماية:**

- **مصدر قواعد واحد**: `AGENTS.md` وقاعدة `Project Profile` + هذا الكتالوج. لا نسخ مختلفة من الـ180 في مهارات متعددة.
- **محرك دورة عمل واحد بحد أقصى لكل مشروع**: Spec Kit **أو** OpenSpec. لا ندمج عمليتي specs في تغيير واحد.
- **EGM خدمة مراجعة اختيارية**: ليس authority ولا verifier ولا بديلًا لاختبارات runtime؛ يفشل كـGoldfish عندما لا تتوفر subagents بسياق جديد.
- **الضوابط الموجودة**: لا نحذف أي عقد/تحقق مثبت من EREI Framework؛ ونستخدمه حسب الأثر والصلاحيات فقط. لا نوسّع مشاريع F5B1/J5/Docker أو learning بسبب هذا القرار.
- **لا تثبيت تلقائي**: أي plugin يحتاج فحص مصدر، إصدار، صلاحيات وصول وكتابة، خصوصية، توافق بيئة المستخدم، وآلية عزل؛ دون تعديلات main/pin قبل اعتماد.

## 3. تخصيص المعيار بحسب المخاطر — ليس كل مهمة مشروعًا كبيرًا

| نوع العمل | العملية الأدنى | مجالات يراجعها الوكيل | أدلة إغلاق مناسبة |
| --- | --- | --- | --- |
| إصلاح موضعي معروف وذو خطر منخفض | وكيل موجود + اختبار RED/GREEN | متغيرات الأمان/العقود مباشرة؛ بقية بنود الصورة N/A بسبب سليم | test مختص، diff محدود، بلا regression |
| ميزة جديدة بواجهة ويب | Spec Kit مختصر (أو OpenSpec) + `AGENTS.md` | 9 مجالات مع اختيار البنود ذات العلاقة | Acceptance scenarios + tests + security/a11y/perf حسب المخاطر |
| تغيير معماري كبير أو متعدد الخدمات | Spec Kit كامل **عند الضرورة** + EGM fresh reviewer إن توفر | Architecture، state، network، security، cache والسطوح الأخرى | Review resolution + code/contract/integration verification |
| مشروع API / data pipeline / desktop | Project-specific profile بديل لسطح الويب + العمليات نفسها | البيانات والتشغيل والأمان أولًا، وحذف بنود SSR/PWA غير المنطبقة | Contract/data integrity/unit/integration/provenance/rollback |

**قاعدة STOP:** عند اختيار بديل أبسط يحقق معيار القبول، لا تُنشأ مرحلة متابعة. عند عدم إثبات فجوة فعلية، لا يُبنى نظام مساعد جديد.

## 4. المفاضلة النهائية بين الاستراتيجيات

| الاستراتيجية | النتيجة المتوقعة (فرضية تحتاج قياسًا) | القرار |
| --- | --- | --- |
| مواصلة Framework الشامل بما فيه محركات تنفيذ وعزل جديدة قبل إثبات فائدة AI | تكلفة تنفيذ/صيانة عالية، خلط جودة العملية بقدرة النموذج | **STOP_EXPANSION**؛ الاحتفاظ بالموجود دون تعميم نجاحه |
| استخدام EGM وحده كبديل كلي | نقد تصميم/توثيق جيد لكن لا يحل المواصفات/إثبات السلوك/بوابات التنفيذ | ليس بديلًا كاملاً |
| تكديس Spec Kit وOpenSpec وBMAD وSuperpowers وEGM | تكرار workflows وتعليمات وتكاليف ومشكلات صلاحية | **REJECT** |
| Codex/وكيل حالي + AGENTS.md + معيار ملائم + اختبارات حقيقية؛ Spec Kit عند المهام الكبيرة وEGM عند مراجعة مهمة | أقل دمج وأقل كلفة محتملة مع الحفاظ على ما ثبت من Framework | **PREFERRED / PILOT BEFORE ADOPT** |
| استبدال Spec Kit بـOpenSpec عندما تثبت تجربة brownfield أنه أخف لنفس النتائج | خفض حجم artifacts مع قبول فقد بعض وظائف Spec Kit | **FALLBACK**، لا نستخدمهما في مهمة واحدة |

**توصية صاحب الدراسة:** `KEEP_EREI_GUARDS_AND_EVIDENCE + REUSE_TOOLS + NO_NEW_RUNTIME`.  
هذا توصيف لطريق العمل، وليس قرارًا هندسيًا معتمدًا لتعديل كود أو إصدار.

## 5. اختبار جدوى قصير يُنتج دليلًا لا مزيدًا من الوثائق

**لا نخلق مشروعات أو أعطالًا مصطنعة** لقياس الأدوات. إذا لم توجد مهمة حقيقية، نغلق مقارنة المصادر الآن ولا نصنع برنامجًا بحثيًا جديدًا.

1. **عند أول تغيير ويب صغير حقيقي:** نفّذ بالوكيل الحالي مع `AGENTS.md` والاختبارات القائمة. سجل حدود التعديل، الملفات المتغيرة، الفشل والتراجع، زمن الإنسان، عدد جولات التصحيح، والتغطية المناسبة للمجالات ذات الصلة. هذه baseline عملية وليست عينة تعميم.
2. **عند أول ميزة حقيقية غير بسيطة:** شغّل Workflow مختصر من Spec Kit من دون فرض كل المراحل، وقيّم اختصار الالتباس ومخاطر التصميم مقابل overhead التوثيق. لا تُعد الميزة نفسها مرتين على قاعدة إنتاج.
3. **إذا احتاج التصميم مراجعة مستقلة فعلاً:** جرّب EGM على **الوثيقة قبل التنفيذ** بعد التحقق من وجود fresh subagent. يُسجَّل فقط اعتراض مبني على مصدر ومؤثر في قرار فعلي؛ لا تقبل عدد الملاحظات معيار نجاح.
4. **مقارنة مرشحة واحدة فقط**: إن ثبت أن Spec Kit بطيء أكثر من اللازم مقابل قيمة التتبع، جرّب OpenSpec على المهمة التالية من فئة مشابهة؛ لا تثبت ثلاثة أطر بالتوازي.
5. **قرار إغلاق:** تبنّ الأداة التي تمنع خطأ مؤثرًا أو تخفض تكلفة بشرية ملموسة دون خسارة جودة التحقق. إن لم يظهر فارق موثق، ارجع إلى الوكيل الحالي والاختبارات وانتهِ.

### المؤشرات التي يجب قياسها فعلًا

- **Correctness**: متطلبات مقبولة وفحوص RED/GREEN/E2E/contract ذات صلة؛ `NOT_RUN` لا تُعد PASS.
- **Security/Privacy**: zero confirmed critical violation + نطاق مراجعة ومخاطر معلنة، لا يقاس بـ'AI said secure'.
- **Scope**: عدد الملفات التي تغيرت دون حاجة، dependencies الجديدة، أي خرق لحدود الملفات.
- **Human effort**: زمن المراجعة/التنفيذ وإعادة العمل الفعليان، والمهام التي أغلقها المالك.
- **Review usefulness**: ملاحظة مدعومة بمصدر غيّرت قرارًا/منعت خللًا، لا عدد المراجعين أو التعليقات.
- **Operational cost**: توكنات/أرصدة/زمن استدعاءات فعلية عند توفر القياس؛ لا تُخمن.
- **Applicability**: البنود التسعة/180 التي تنطبق فعلًا مع `N/A` مبرر، لا نسبة وهمية 'تغطية 180/180'.

**لا نستنتج causality أو تفوقًا عامًا من مهمة أو مهمتين.** هدف التجربة قرار اعتماد محلي محدود، لا ورقة benchmark.

## 6. النتيجة النهائية المشروطة

**القرار الأنسب الآن:** لا نكمل إعادة اختراع إطار متعدد الوكلاء/المواصفات/الأدلة. نوثق 180 مفهومًا كـ**قائمة مراجعة اختيارية بحسب التقنيات والمخاطر**؛ نحتفظ بـFramework الحالي وقواعده ودفاتر الأدلة دون توسع؛ نجرّب Spec Kit **كمرشح أول لتنظيم المهام المتوسطة والكبيرة**، وEGM للمراجعة التصميمية ذات قيمة؛ OpenSpec بديل محتمل عند ثبوت overhead. نستخدم أدوات التحقق الأصلية للمشروع لقياس النتائج.

**التفريق الحاسم:** كتالوج 180 ليس برهان امتثال، ولم نشغّل أي من هذه الأنظمة على مشروع المستخدم في هذه المراجعة. لذلك التوصية **مستندة إلى ملاءمة قدرات المصدر** وتبقى خاضعة لتجربة مناسبة وموافقة على تثبيت الإضافات وصلاحياتها.

**لا يُنفّذ تلقائيًا:** تعديل `CONSTITUTION.md`/قواعد المشاريع القائمة، تركيب إضافات، نقل Stable pin، تبديل أدوات التنفيذ، فتح تطوير F5/J5/Agent OS، تغيير نظام الصلاحيات أو التجارب الحية. هذه حزمة تقييم وتوثيق للقرار فقط.
