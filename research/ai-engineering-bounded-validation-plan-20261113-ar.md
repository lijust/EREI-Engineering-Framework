# خطة اعتماد محدودة — اختبار قيمة المنظومة قبل تعديلها

**التاريخ:** 2026-11-13  
**الحالة:** `PREREGISTERED_PLAN_DRAFT` — ليست موافقة على تثبيت EGM/Spec Kit أو استدعاء نموذج/تنفيذ أدوات.  
**النطاق:** استخدام قواعد EREI الموجودة ومعايير UER الجديدة كمرجع مراجعة فقط، ثم مقارنة قيمة إضافة محددة عند وجود مهمة حقيقية.  
**الحد النهائي:** **مهمتان حقيقيتان كحد أقصى** من أنواع مختلفة؛ لا توسيع دوري أو تجارب لتبرير درجات أفضل. لا تحريك لأي Project `framework.json` pin.

## 2. اختيار السيناريوهات دون اختبار مزيف

- **المهمة A — أول عطل حقيقي محدود** في EREI 3.2/مشروع مشابه: السلوك المكسور مثبت، مع RED witness وصلاحيات غير إنتاجية. نستخدم EREI الموجود كـbaseline، ونختار فقط UER IDs ذات العلاقة. **لا حاجة إلى تثبيت Spec Kit** لمجرد إصلاح بسيط.
- **المهمة B — أول ميزة أو تغيير تصميم ذي أثر حقيقي**: متطلبات وسياق فعلي قبل التنفيذ. إذا ظهر قرار معماري يحتاج رأيًا مستقلاً، نقيّم **EGM Goldfish** *في قراءة فقط*، بشرط إثبات وجود subagents مع سياق منفصل في harness المحدد. إذا لم يتوفر، نسجل `NOT_RUN` ونستخدم مراجعة بشرية ولا نزعم أنها Goldfish.
- **اختيار Spec Kit أو OpenSpec لا يتم إلا إذا** أظهر مسار EREI في مهمة B فجوة واضحة في التتبع/المواصفات أو تكلفة مراجعة مفرطة. عندها نُجري مقارَنة تصميم/خطة **دون تطبيق الكود مرتين في الإنتاج**. استخدام fixture تاريخية مسموح لاختبار قابلية تشغيل الأداة، لكنه لا يثبت إنتاجية جديدة.

## 3. مدخلات مجمدة قبل أي عمل

لكل مهمة:
- `task_id`، repo/ref/source blob، العارض/السلوك، stack/surface، المخاطر، owner، الصلاحيات، حدود التعديل.
- معايير القبول المعلنة، `UER IDs` المنطبقة والـ`N/A` المبررة، الاختبارات الموجودة، حالة CI.
- `human baseline` بحدود واقعية: زمن مراجعة بشري أو سجل سابق من نوع مماثل **مع تمييز اختلاف الظروف**.
- نسخة الأداة والمهارات/الموديل الفعلية، ولو لم تنفذ أداة يتم تدوين `NOT_RUN`.
- محدد مسبقًا: أي تغيير في أسرار أو قواعد إنتاج أو صلاحيات عالية المخاطر => STOP / human approval.

## 4. المخرجات المطلوبة ومعايير القبول

| معيار | يقبل فقط بدليل | يرفض عند |
| --- | --- | --- |
| Correctness | اختبارات تخص السلوك المطلوب + كود الخروج + SHA | الادعاء بأن AI صحح المشكلة دون اختبار |
| Non-regression | اختبارات مسار متأثر/contract حسب مستوى الخطر | فشل جديد غير مفسر أو مخفي |
| Scope | diff files / dependencies ضمن المسموح | تعديل خارج الحدود أو توسع بلا حاجة |
| Quality | مبدأ UER ذو علاقة مرتبط برصد/مراجعة فعلية | 180 بندًا مسجلًا PASS دون تطبيق |
| Risk | أمن/خصوصية وسلامة بيانات/rollback حيث تنطبق | حادث حرج أو صلاحية غير مصرح بها |
| Cost | زمن عمل بشري وجولات إعادة العمل ومجهود المستندات | وقت مجهول يعرض كتحسن مثبت |
| EGM value | ملاحظة واحدة على الأقل مستقلة ومسنودة بمصدر **منعت خطأ مؤثرًا أو غيّرت تصميمًا مبررًا**، مع عدم تجاوز بوابات الجودة | مراجعة ذات تعليقات شكلية فقط أو لم تُجرَ |
| Alternative-workflow value | فجوة/تحسن قابل للمراجعة لا يوفره EREI دون تعقيد زائد | تكرار مخرجات/specs ولا دليل فائدة |
| Evidence | مصدر مميز `OBSERVED` أو `OPERATOR_REPORTED` أو `HUMAN_REVIEWED` | التعامل مع mock/دليل وثائقي كأنه اختبار إنتاج |

**لا نجعل «تقليل الزمن» أو «عدد الملاحظات» شرط قبول رقمي مصطنع.** إن لم يمكن قياس أثر عملي، نترك الادعاء `NOT_ESTABLISHED` ونغلق المهمة بدون نشر ترقية.

## 5. أوامر/عمليات مسموح بها في التقييم الحالي

**الآن مسموح:** قراءة الملفات، كتابة وثائق بحث، مراجعة المصدر، إعداد خريطة متطلبات، اقتراح قرار ومناقشته داخل Draft PR.

**ليس في النطاق:** تثبيت أي plugin خارجي، تغيير `AGENTS.md` أو الـFramework pin أو EREI runtime، تشغيل Gemini/API، نشر/تغيير قواعد إنتاج، إنشاء CI/runner، نقل نماذج إلى Docker، ترقية Stable، تنفيذ مهمة هندسية مصطنعة، محو أو تعديل أدلة سابقة.

لا يتوسع هذا التفويض تلقائيًا عند نجاح أي دراسة مصدرية.

## 6. قرار الإغلاق

| المخرج من مهمتي التقييم | التصرف |
| --- | --- |
| EREI + UER + tests يغطيان المهمة والقبول | **KEEP_EREI**؛ أغلق ولا تضف framework |
| EGM يضيف مراجعة مستقلة ذات أثر فعلي | **ADOPT_EGM_AS_OPTIONAL_REVIEW** مع مراجعة أمن/صلاحيات واختبار harness لاحق مستقل |
| Spec Kit/OpenSpec يزيل فجوة واضحة في EREI | **REPLACE_ONE_WORKFLOW_ONLY** بمرشح واحد بعد موافقة منفصلة؛ لا تكديس |
| النتيجة مختلطة/محدودة/غير قابلة للقياس | **NO_CHANGE / NOT_ESTABLISHED**، لا تستنتج تفوقًا |
| تحتاج الموافقة أو اختبارات CI/الأمان غائبة | **BLOCK_APPROVAL**، وثق الناقص بدل الادعاء |

**نقطة الإغلاق الأساسية:** عند الانتهاء من المهمتين (أو عدم ظهور حاجة حقيقية لاعتماد أداة جديدة) تُغلق المراجعة. أي تجربة إضافية تتطلب هدفًا جديدًا ودليل ضرورة صريح؛ لا يُنشأ طور تطوير تلقائي.

## 7. الخطوة المطلوبة قبل اعتماد التنفيذ

راجع المالك ثلاث قرارات فقط في Draft PR:
1. هل UER-01..32 تحقق هدف التوجيه الهندسي الشامل مع إقرار أن معايير المجال التنظيمي تحتاج متخصصًا؟
2. هل نُبقي Workflow EREI الحالي كأساس ونجعل EGM اختياريًا بدل اعتماد Spec Kit إجبارياً؟
3. هل نوافق على **التقييم في مهمتين حقيقيتين فقط** دون تثبيت أدوات أو توسيع runtime قبل ظهور الحاجة؟

بعد اعتمادها فقط، يمكن تحديد مهمة حقيقية مناسبة. لا نحتاج إنشاء مستودع جديد ولا اختبارات لتأكيد 32 متطلبًا نظريًا الآن.
