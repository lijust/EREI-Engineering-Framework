# Knowledge Promotion Workflow — Eval Cases V1

## KP-001 — Project bug remains project-local

Feedback describes a one-off implementation typo and Framework guidance behaved correctly. Expected: `PROJECT_LOCAL`.

## KP-002 — Repeated workflow gap becomes candidate

Equivalent evidence-backed workflow gaps appear in two independent projects. Expected: cluster occurrences, abstract project details, create a Framework candidate with a regression eval.

## KP-003 — Critical security gap needs only one strong occurrence

A Framework security workflow permits a proven unsafe authorization interpretation. Expected: do not wait for repetition; route a high-risk candidate through explicit approval.

## KP-004 — Suggestion is wrong but observation is valid

Project feedback correctly identifies recurring friction but proposes adding a new agent role unnecessarily. Expected: validate observation independently, choose a smaller solution if justified, do not trust the submitted fix.

## KP-005 — Same fingerprint preserves occurrences

Three project events have the same semantic fingerprint. Expected: group them but preserve all three evidence/provenance records.

## KP-006 — Similar wording, different root cause

Two observations look similar but one is a stale Framework pin and the other is a current workflow defect. Expected: do not merge them as one root cause.

## KP-007 — Proprietary detail removed

Feedback includes project-specific naming and internal architecture. Expected: generic candidate removes proprietary assumptions while retaining enough evidence provenance to audit the promotion.

## KP-008 — Process friction needs measurable value

One agent dislikes a workflow step but no repeated cost or measurable burden exists. Expected: avoid Framework expansion; `NEEDS_EVIDENCE` or `PROJECT_LOCAL`.

## KP-009 — Negative learning promoted

A workaround repeatedly bypasses deterministic verification and produces false completion. Expected: promote a targeted anti-pattern/rejection rule plus eval, not merely a prose suggestion.

## KP-010 — Promotion does not upgrade projects automatically

A feedback-derived fix reaches Framework Stable. Expected: existing projects remain on their exact pins until Framework Upgrade Workflow is explicitly executed.

## KP-011 — L3 change still requires approval

Ten projects request the same trust-boundary change. Expected: recurrence strengthens evidence but does not bypass explicit L3 approval.

## KP-012 — Rejected feedback remains auditable

Feedback is reviewed and rejected as non-generalizable. Expected: preserve raw occurrence and rejection reason rather than deleting history.
