# تمرين rollback لـTask Learning

## تحديث إعداد الهدف — 2026-10-23

تمت محاذاة مسودة T14 على Framework main النهائي `58034ae3e6eca6b2e45f79453aa71a783beee07c`؛ PR #94 ما زال **DRAFT / غير مدمج**. يجب تشغيل التمرين من checkout معزول ونظيف عند SHA محدد؛ الأداة ترفض `--target-ref` المخالف لـ Git HEAD قبل تشغيل أي حالة. اسم V2 ref داخل بيانات الاختبار يمثل SHA الفعلي للـcheckout فقط، **ولا يثبت consumer pin أو activation**.


النطاق: إعداد T14 في Issue #81. هذا تمرين تكامل ببيانات مصطنعة، وليس اعتماد
Internal Release أو أمرًا لترحيل مشروع. يعتمد على إصلاحات F01–F03 في PR #88؛
لا يثبت activation أو سلوك نموذج مستقل أو تكامل جميع إصلاحات الإصدار.

## ما الذي يجب إثباته؟

V1 Stable عند `69079018606750312344cb3c648952b9ab72d35b` يرفض
`schema_version=2`. لذلك إعادة `.erei/framework.json` وحدها لا تعيد قابلية
استخدام سجل مختلط. لا نحوّل أحداث V2 إلى V1، ولا نحذف سجلات التجربة، ولا
نعيد ترقيم `EPOCH` أو نعيد حساب fingerprints التاريخية.

الرجوع المدروس يفصل ثلاثة أشياء:

1. نسخة V1 قبل التجربة، تشمل pin وملفات `.erei/learning/` كاملة.
2. أرشيف كامل لحالة تجربة V2 عند الإيقاف، يشمل immutable events/reviews
   وJSONL وترتيبهما والحالة المشتقة وpin التجربة.
3. نسخة جديدة مستعادة من baseline V1. تبقى كتابة V1 بعد الرجوع تاريخًا
   منفصلًا عن أرشيف V2؛ إعادة جمع التاريخين تحتاج reconciliation معتمدًا.

حفظ bytes لا يكفي وحده: يجب أن يظل أرشيف V2 قابلًا للتحقق بأداة V2 المثبتة،
مع نفس occurrence IDs وعضوية المراجعات وverification escapes المعلقة.
إرجاع لوحة V1 إلى حالة قديمة لا يغلق التزامات مراجعة V2. عند وجود
`IMMEDIATE_REVIEW` في الأرشيف يجب حمل هذا الالتزام إلى قرار الاستئناف؛
لا يجوز إخفاؤه لأن النسخة المستعادة لا تحتوي الحدث.

## تشغيل التمرين

من checkout معزول يحتوي إصلاحات PR #88:

```text
python -B tools/tests/drill_task_learning_rollback.py --v1-tool <exact-export>/task_learning.py --target-ref <exact-40-hex-checkout-HEAD>
```

ملف V1 المطلوب هو bytes الأصلية لـ`tools/task_learning.py` من commit أعلاه:

- Git blob: `8429a5fdda91f962e067f30e0a828a1789850ec3`
- SHA-256: `336037ea356c91d780f61684889b7c92c5d2bde21a8fff2591fec95e559be8f2`

صدّر المصدر من Git دون تحويل line endings. إذا كان commit موجودًا محليًا،
يمكن تنفيذ المقتطف التالي داخل مستودع Framework؛ ينشئ مجلدًا مؤقتًا ويطبع
مسار الملف دون الكتابة داخل المستودع أو استدعاء الشبكة:

```python
from pathlib import Path
import subprocess
import tempfile

source = subprocess.run(
    ["git", "show", "69079018606750312344cb3c648952b9ab72d35b:tools/task_learning.py"],
    check=True, stdout=subprocess.PIPE,
).stdout
destination = Path(tempfile.mkdtemp(prefix="erei-v1-export-")) / "task_learning.py"
destination.write_bytes(source)
print(destination)
```

يرفض التمرين أي bytes مختلفة قبل تنفيذ أداة V1، وينفّذ النسخة التي تحقق
منها مباشرة. لا يحمّل أداة V1 من الشبكة ولا يستدعي GitHub Actions.
يتحقق من Git root وSHA الفعلي والنظافة باستخدام Git الحقيقي؛ وإلا يفشل قبل
إنشاء بيانات fixtures. لا يثبت ذلك أن الـrunner أو مخزن الأرشيف أو مشغّل
التطبيق آمن تشغيليًا. يلزم مراجعة نتيجة التمرين على نفس target الـInternal
المثبت بعد قبول المصدر/المراجعات، دون الكتابة لأي consumer.

يستعمل `TemporaryDirectory` لجميع مشاريع الاختبار، ولا يقبل project path
من المستخدم. يختبر أداة V2 المجاورة للسكريبت ويطبع hashes المصدر؛ يجب
ربطها بـcommit/tree المراجعة عند الاحتفاظ بالنتيجة.

هذا اختبار opt-in، واسمه لا يطابق `test_*.py`. لا يُضاف إلى كل تشغيل CI
لأنه يحتاج مصدر V1 الأصلي؛ يجب تشغيله صراحة عند تأهيل target النهائي.
النتيجة JSON على stdout والتفاصيل على stderr، وexit code غير صفر عند الفشل.

## السيناريوهات ومعايير النجاح

- تولّد أداة V1 الأصلية حدثين ومراجعة بترتيب إضافة مخالف لترتيب timestamps.
- تضيف V2 حدثًا وتغلق مراجعته، ثم تسجل verification escape غير مغلق.
- تغيير pin فقط يجعل `V1 validate/status` يرفضان السجل المختلط، دون تعديل
  الملفات. هذا الفحص لا يدّعي أن كل أوامر V1 آمنة على سجل مختلط؛ لا تشغّل
  `capture` أو `close-review` لـV1 على أرشيف V2.
- الاستعادة تتم بالنسخ إلى destination جديد، مع مقارنة كل الملفات bytes
  قبل أي تشغيل. تتطابق سجلات V1 وpin بعد `status`؛ يسمح بتجدد derived state.
- يظل الأرشيف مساويًا لحالة التجربة كاملة، ويقبل V2 snapshot أربعة أحداث
  ومراجعتين. المراجعة التاريخية تغطي حدثي V1 فقط، ومراجعة V2 تغطي حدثها فقط.
- يظل الحدث الرابع خارج المراجعات، مع escape واحد و`IMMEDIATE_REVIEW`.
- كتابة حدث V1 جديد في النسخة المستعادة لا تغير baseline أو أرشيف التجربة،
  ولا تدّعي دمج التاريخين.
- يُرفض مصدر V1 المعدّل دون تنفيذه.

## حدود الإثبات وقبول Internal Release

هذا اختبار استعادة من snapshots ساكنة ضمن process واحد على ملفات محلية.
لا يختبر انقطاع الكهرباء أو disk-full أو concurrent writers أو صلاحيات
مخزن الأرشيف أو disaster recovery أو rollback للتطبيق نفسه. الـpin داخل
الاختبار metadata مصطنعة؛ لا يثبت تنفيذ resolver أو نجاح pin upgrade.
لا توجد نسخة V2 إلى V1 lossless in-place migration مثبتة.

قبل تأهيل Internal Release:

1. قبول إصلاحات T01/T02/T03/T04/T05/T07/T08 بالمراجعة المناسبة.
2. تثبيت commit/tree واحد للنطاق، ثم تشغيل regression والتمرين عليه.
3. إيقاف writers قبل snapshot، وحفظ الأدلة في موقع منفصل لا يستطيع runtime
   التجريبي تعديل baseline فيه، والتحقق من hashes واكتمال النسخة.
4. تسجيل snapshot IDs ومواضع الاستعادة وأحداث التجربة والتزامات المراجعة
   المعلقة ومسؤول reconciliation. لا يكفي حفظ archive غير قابل للقراءة.
5. إجراء مراجعة مستقلة للنتيجة وتحديد صلاحيات ومدة وبيانات التجربة. أي
   تغيير consumer pin أو سجل حي يحتاج موافقة مستقلة، ولا يجيزه هذا الملف.

عند فشل مقارنة الملفات أو تغير العضوية أو تعذر قراءة الأرشيف، يبقى الرجوع
غير مقبول ويوقف الاستئناف. لا تعالج ذلك بحذف أحداث أو تخفيف validation.
التراجع عن هذا PR يحذف إعداد الاختبار فقط، ولا يتضمن تعديل بيانات مشروع.
